# MineDojo 自主 Agent 详细计划

## 一、目标与约束

主要在 `model_agent.py` 实现自主 Agent，覆盖 `practice-scenes.json` 的三个独立场景：

1. 木制工具链：从空背包推进至木镐。
2. 石器工具链：获取木镐、圆石、石镐和熔炉。
3. 完整场景：从零推进至铁镐。

优先在每局预算内稳定、尽快完成当前目标，同时减少无效环境动作与模型调用耗时。煤、火把支线和死亡扣分不是主要优化目标；但燃料、避险和脱困是完成主线的必要条件。完整局首次合法获得铁镐时结束，因此不会为了额外分数主动延迟主线。

使用 Python 标准库在 `model_agent.py` 内实现显式状态图，不引入 LangGraph 或其他额外第三方依赖。保留 `evaluation_adapters/`、评分逻辑、动作目录和现有场景，不修改评测设施。复用 `ModelClient` 和 `minecraft_actions.py`；使用 `pack_agent.py --policy model` 将策略打包成 ZIP 根目录的 `agent.py`。

## 二、整体结构与运行接口

保留项目约定的 `Agent` 类及其三个接口：

- `configure(config)`：读取框架传入的模型和策略配置，初始化模型客户端、参数及状态容器。
- `reset(goal)`：接收当前场景的目标列表，清空本局规划、搜索记忆和动作状态。每个场景单独初始化，不依赖上一局。
- `act(observation)`：每个环境步接收最新公开观测，推进状态图并返回长度为 8、每项均为普通 Python 整数的合法动作。

状态图采用代码中明确可辨的节点和转移条件，不依赖额外框架：

1. **观测整理**：规范化背包、坐标、朝向、生命值、准星命中、附近设施、可制作提示和上一步反馈。
2. **反馈核验**：确认上一动作是否产生预期变化，更新进度及失败次数。
3. **任务规划**：结合目标、已有材料、装备和设施确定当前子目标。
4. **动作决策**：选择确定性操作、执行已有短动作片段，或按需请求视觉模型。
5. **恢复处理**：识别卡住、连续操作无效、位置或背包突变、模型错误等情况，执行有限恢复或重新规划。
6. **合法性检查**：基于 `noop_action` 构造动作，检查维度、类型和边界；异常时返回合法保守动作。

每步都重新读取观测并检查当前行为是否仍适用。记忆是待验证的线索，不取代环境事实；状态转移应能在目标变化、操作失败或环境突变时提前中断当前动作。

## 三、任务分解与资源管理

建立覆盖三个场景的主线依赖关系：原木 → 木板与木棍 → 工作台 → 木镐 → 圆石 → 石镐与熔炉 → 铁矿石及燃料 → 铁锭 → 铁镐。

- 根据 `goal` 确定场景所需的目标范围，不强制教学场景继续推进铁器。
- 从背包记录汇总物品数量并保留实际槽位，处理必要的原木及木板变体；根据当前库存和已经存在的设施计算材料缺口，预留后续制作所需材料。
- 分别记录历史上已达成的阶段与现在拥有的资源。历史达成不代表工具和材料仍在，消耗、损坏、丢失或可能死亡后须重新规划。
- 对工作台、熔炉记录可能的位置；需要时检查 `nearby_tools`、背包变化与后续行为，不能仅凭记忆认定设施可用。
- 将 `craftable` 当作环境提示，而不是成功保证；合成和冶炼之后依据后续背包变化确认。
- 按完成冶炼所需获取适当燃料，不把煤或火把支线作为单独追分目标。

配方细节、设施交互范围、燃料消耗、熔炼时长以及某些物品变体的表现，需要结合现有接口与服务器实际环境确认；实现中对失败设置边界，不将未经验证的假设当成事实。

## 四、感知、导航与采集

- 优先使用结构化观测：背包和装备、坐标、朝向、生命值、准星射线、附近设施和 `last_action`。`crosshair_hit` 仅是 10 米内准星方向最先命中的信息，不能穿墙，也不意味着命中目标必然在可交互距离内。
- 需要识别画面中的树木、石头、矿物、道路或障碍时，向视觉模型发送当前图像和精简状态，取得可校验的有限决策；不假设 Agent 拥有完整地图。
- 保存轻量级本局记忆，包括已探索位置、发现的资源和设施、最近失败区域。接近目标后根据新观测重新验证，避免将陈旧信息视作资源仍存在。
- 移动采用有限长度的动作片段；接近目标、转向、瞄准、挖掘和放置时缩短执行周期。每步根据位移、准星、生命和背包变化判断是否应中止。
- 按目标方块及库存选择和装备合适工具。持续攻击时检测目标是否仍在准星、是否产生材料变化；限制重复次数，必要时调整视角、重新接近或搜索其他目标。
- 利用滚动反馈检测连续无位移、无资源变化、反复失败等现象，按有限次数尝试保守脱困、切换目标或重新规划，避免无限循环。
- 以生命值骤降、位置突变和背包变化作为可能死亡或重生的线索，而不是当作官方死亡事件；发生突变后重建当前资源与装备状态。

## 五、模型调用与预算

- 继续使用 `ModelClient(config=config)`，不在 Agent 代码中写死模型名、接口地址或密钥。
- 从固定间隔调用改为事件驱动：首次需要判断场景、搜索新资源、连续无进展、视觉目标丢失或复杂恢复时调用；常规合成、装备和已验证的短动作优先使用规则。
- 配置最小调用间隔、动作片段长度、无进展阈值和有限重试等非敏感参数，并在代码中提供默认值；避免每环境步均发起请求。
- 对模型输出进行结构、字段、类型、范围和当前状态适用性校验。解析失败或调用异常时执行有限恢复与保守回退，不让错误输出直接成为游戏动作。
- 对超时或传输失败限制重试，考虑上游请求可能已计费；避免无限等待及重复请求。
- 模型思考时间计入完整局墙钟预算。降低调用次数不能以长时间无效行动为代价，具体阈值需通过服务器结果校准。

## 六、一次性模型配置迁移

`模型配置.txt` 仅用于本次提供模型参数，不是策略运行依赖、开发模块或提交内容：

1. 实施时一次性读取其中的模型名称和完整 API 请求地址，写入 `config.json` 的 `model.name`、`model.api_url`。
2. `config.json` 的 `model.api_key` 留空。密钥只由目标服务器的 `UESTC_MODEL_API_KEY` 环境变量提供，不写入 JSON、日志或提交包，也不在回复中展示。
3. Agent 从框架传入的 `config` 读取配置；`ModelClient` 读取配置与环境变量。运行时不读取 `模型配置.txt`。
4. 在 `config.json` 的 `agent` 中设置必要的非敏感参数，保留默认值。正式评测由平台提供模型配置，保留选手的策略参数。

当前仅能确认项目客户端使用 Chat Completions 请求结构；配置中的服务是否支持该协议、模型是否支持图像输入，必须在目标服务器确认。不会擅自将现有客户端改为 Responses 协议。

## 七、Docker 与打包兼容

以官网和用户提供的 Docker 命令为基准：

- 使用比赛镜像 `docker.io/streetartist/uestc-minecraft-controller`、`linux/amd64` 和给定的 CPU、内存、共享内存及进程限制。
- 保持宿主目录挂载至 `/workspace`，容器工作目录为 `/tmp`，保留 `PYTHONPATH=/workspace`、`PYTHONDONTWRITEBYTECODE=1` 及 `xvfb-run` 入口。
- 由 `/workspace/practice.py` 加载 `/workspace/agent.zip` 和 `/workspace/practice-scenes.json`，结果输出到 `/workspace/practice-output`。
- Agent 不假设当前工作目录为脚本目录；若读取随包资源，需要以 `__file__` 为依据定位，不能依赖 Windows 路径或文本配置文件。
- 使用 `pack_agent.py --policy model --output agent.zip`，确保 ZIP 根目录包含运行入口 `agent.py` 和现有辅助文件；不要求在比赛镜像内额外安装 LangGraph 或其他依赖。
- 用户提供的原命令含 `--network none`，适用于离线示例。模型策略需要访问外部服务，按官网要求移除该选项，并添加 `-e UESTC_MODEL_API_KEY` 把已设置的变量传入容器。资源、挂载及入口参数保持原样。
- 交付服务器启动说明时，确保 PowerShell 的 `$Work`、`$Image` 分别独立赋值，续行反引号后不带空格。

## 八、实施顺序

1. 核对目标、动作目录及现有辅助接口，建立状态结构、观测整理和合法动作生成。
2. 实现目标依赖、材料缺口计算、设施与工具状态、确定性动作和反馈核验。
3. 实现视觉模型的受约束决策、有限动作片段和本局搜索记忆。
4. 实现卡住、无效操作、模型异常和可能重生后的有界恢复。
5. 一次性将非敏感模型配置及策略参数写入 `config.json`，密钥留空。
6. 检查 ZIP 入口、随包依赖和 `/tmp` 工作目录约束，准备服务器运行说明。

## 九、验证与交付边界

根据你的要求，本机不运行 MineDojo、Docker、练习场景或模型 API，不生成提交 ZIP，也不把凭据发送至外部服务。

本机仅对修改后的 Python 使用 `ast.parse` 或 `compile` 做不生成字节码的语法检查，解析 JSON 检查配置结构，并静态检查提交入口与依赖。语法检查通过不代表模型接口可用、游戏动作正确或三个场景已经完成。

交付后由目标服务器配置环境变量、打包，并依次验证：模型接口及图片能力、`woodcraft`、`stone-tools`、`iron-age`、多种子场景。通过 `steps.jsonl`、`result.json` 和回放重点检查转向刻度、触及距离、挖掘耗时、配方和熔炼行为、模型调用耗时、卡住恢复及成功率。未实测前不承诺三个场景一定成功。
