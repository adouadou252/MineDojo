# 木器 Agent 优化计划

## 1. 本轮范围

只优化原木 → 木板、木棍 → 工作台 → 木镐这一条木器链。

- 保留 `practice.py` 和 `practice-scenes.json` 的三个场景，不修改场景选择逻辑。
- 在服务器现有启动命令末尾添加 `--only woodcraft`，仅运行木器教程。
- 修改主要集中在 `model_agent.py`；仅按实际需要调整 `config.json` 的非敏感 `agent` 参数。
- 不新增石器、找矿、开路或冶炼逻辑。已有后续配方保留，但不作为本轮优化和验收对象。
- 保持标准库和现有随包助手，不添加第三方依赖，不改模型客户端、评测器或评分规则。

## 2. 诊断依据与优先级

木器教程第1185步才首次获得原木，最终1500步结束，只完成原木、木板和木棍。原木名称兼容和实际攻击已经生效，不能再将失败归为旧版本或 `wood` 未识别。

明确事实：

- 长时间停在寻找原木；恢复频繁，fallback多，未形成稳定资源进展。
- 获取原木后，基础合成可以迅速推进。
- 工作台和木镐未完成，整体材料收集不足。
- 存在模型请求错误，但没有证据证明它是唯一或主要原因，也不能确定HTTP400的具体原因。

源码风险：拾取状态短、依赖不恰当的射线门控；材料按单个目标递归，缺少木器链整体备料；恢复调度污染资源进度时间；阶段状态可残留。

修复优先级为：真实进度与诊断 → 木器整体备料 → 找树和接近 → 连续采集与拾取 → 工作台操作 → 模型错误期间的恢复。

## 3. 建立明确的木器子状态图

为木器任务定义有限阶段：

`备料规划 → 找树 → 接近树干 → 对准 → 挖掘 → 确认/拾取 → 基础合成 → 放置工作台 → 工作台合成 → 木镐确认`

每一阶段保存必要上下文、开始步数、期限、成功条件和失败转移，不再用一个笼统的 `gather log` 包含所有行为。

- 每步先核对库存、上一动作结果和当前目标是否仍适用。
- 阶段变化时清理旧动作片段，但保留仍有效的树木位置、拾取目标和工作台线索。
- 资源入包、合成确认、设施确认分别记录，不能凭模型回答宣布完成。
- 历史里程碑与当前持有材料分开管理。

## 4. 木器链整体备料

以默认场景配方计算，工作台需要4块木板，木镐需要3块木板和2根木棍；制作一批木棍消耗2块木板。因此从空背包完成木器链至少需要9块木板，即通常3个原木产出的12块木板。

实现时根据现有库存、设施和实际配方反馈动态扣减，不无条件固定采集3个原木：

- 木器开局计算完整材料缺口，优先在已找到的树附近备齐，而不是每完成一个中间目标就重新找树。
- 使用同一棵树剩余可触及木块的观测线索；只有目标失效、材料足够或路线不安全时才离开。
- 预留工作台、木棍和木镐的材料，避免中间制作耗尽剩余木板。
- 先满足可携带材料，再去工作台，不在材料不足时反复返台。
- 超时或资源丢失后根据真实库存重新计算，避免重复制作已满足的物品。

数量是依据当前配方的预期，最终以背包反馈核验。

## 5. 找树与接近

### 持续搜索目标

- 记录当前搜索方向或候选树木位置、起点、期限和失败次数。
- 模型负责从图像选择可见树干、合适方向和短导航动作；规则负责维持有效目标、检查位移和准星距离。
- 对相同区域反复转向但没有新增线索时，明确切换搜索方向或局部区域，不每次清空上下文重新选择。
- 搜索记忆有界，记录实际探索和失败，不把转向次数当作有效探索。

### 接近与对准

- 准星命中 `wood` 等原木方块后保留坐标，逐步接近。
- 距离较远时检查是否实际缩短；近处减小动作长度，先调整视角，再依据下一步准星确认攻击。
- 路径不确定、出现液体或明显落差时重新观察，不凭目标坐标盲目前进。
- 视角恢复优先修正极端俯仰，减少只看天空而持续水平旋转。

## 6. 连续挖掘与拾取闭环

- 沿用统一的木材匹配规则，规则执行器和模型过滤器共用判断。
- 目标仍有效且可触及时稳定攻击，减少中断挖掘的无关动作。
- 目标变化只标记“疑似破坏或视线变化”，不直接断言产生掉落。
- 保存原方块位置、资源数量基线和拾取总期限。当前射线变成远处背景或无命中时，不直接丢弃拾取意图。
- 依据保存位置、实际位移、视觉信息和安全反馈决定接近；不确定时让模型处理拾取，保留该目标上下文。
- 原木数量增加则确认成功；到达附近并有限检查仍未增加，或超过总期限，记录原因后重新采集。
- 需要更多木材时，优先检查当前树剩余木块，不立刻进入全新搜索。

新增拾取开始、资源确认、目标失效、超时等日志。由于现有记录不能确认每次木块变化的真实原因，优化后应让这些事件可追踪。

## 7. 工作台与木镐操作

- 材料满足后按实际需求制作木板、木棍与工作台；每步检查背包变化。
- 模型辅助选择放置位置和朝向，规则核验真实槽位与允许操作。
- 区分已验证工作台方块坐标、放置估计位置和稳定接近点，不把不断变化的玩家坐标当作准确设施位置。
- `nearby_tools.table` 为真后执行木镐制作，并以木镐入包确认完成。
- 放置、靠近和合成均有明确等待期限及失败处理。返台无进展时重新定位，不能无限往返。
- 不新增GUI合成或修改环境交互协议，继续使用现有动作助手。

## 8. 进度计时与分级恢复

分别维护：

- 最后获得目标资源的步数。
- 当前任务和阶段开始步数。
- 最后有效导航进展步数。
- 最后恢复调度步数。

执行恢复、搜索超时或转向不能更新资源进展时间。

恢复按原因分级：视角校正 → 有界绕障 → 更换局部路线 → 模型重新规划。每级必须检查实际位移、目标距离或视野改善，连续失败则升级，而不是重复4步短动作后重新计时。

模型冷却期间继续已经确认有效的短动作或确定性采集、合成；缺少安全依据时才观察等待。不会为了减少noop而盲目前进。

## 9. 模型与日志

- 保留现有配置读取及环境变量凭据方式，不读取 `模型配置.txt`。
- 提示词聚焦当前木器阶段、材料缺口、当前目标和最近失败，控制上下文大小。
- 维持请求/解析/校验失败分类，补充固定失败原因、请求耗时与安全状态码。
- 格式或动作校验失败时，将具体原因反馈给下一次决策；传输和上游错误按类别有限退避，不无限立即重试。
- 不擅自调整服务协议，不猜测HTTP400原因，不打印原始响应、图片、鉴权信息或密钥。
- 定期摘要输出材料缺口、任务和阶段停留时间、有效导航、实际攻击、拾取结果及恢复效果。

## 10. 参数调整原则

仅增加行为所需的木器搜索、接近、拾取、阶段期限和恢复参数，集中放入 `config.json.agent` 并提供默认值。

不通过扩大1500步上限、修改场景或增加模型预算掩盖问题；参数初值根据已有日志合理设定，效果由服务器单局验证后校准。

## 11. 实施与验证边界

实施顺序：状态和真实计时 → 整体备料 → 搜索接近 → 挖掘拾取 → 工作台木镐 → 故障恢复和诊断 → 只读审阅。

遵循你最近的要求：本机只写代码并只读审阅，不执行Python、语法编译、测试、打包、Docker或模型请求。交付时明确本轮未运行检查。

服务器使用现有打包方式重新生成 `agent.zip`，在原Docker命令末尾加 `--only woodcraft`。分阶段核验：

1. 找到并接近树干，输出实际攻击。
2. 取得第一份原木，并连续备齐木器材料。
3. 制作并放置工作台。
4. 确认木镐入包，最终为 `tutorial_goals`。

重点比较首次原木步数、备料完成步数、拾取停留、恢复耗步和木镐完成步数；不以模型成功响应次数作为能力达标指标。本轮不宣称石器或铁器能力已经实现或验证。
